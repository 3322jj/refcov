# 第 0 步权限实测结果

EN summary: Before building layer 2 (registering reference material through one MCP write tool that the user approves in Kiro's permission prompt), we checked on 2026-11-17 whether a user-level `ask` rule on one MCP tool really makes Kiro ask every time. We put `ask` on the read-only tool `refcov-test/check` in a test folder and called it in Kiro IDE and kiro-cli 3.3.0. Every IDE call asked, in Supervised, Accept file changes and Approve for me; the prompt shows the tool name, the tool card above it shows the argument values, and the prompt offers no "Always allow" for that tool. An `autoApprove` entry in the workspace MCP config did not skip the prompt even for a tool with no rule, so we could not show which of the two wins; no bypass was seen. kiro-cli with `--trust-all-tools` ran the tool without asking, as Kiro's documentation says; without that flag the non-interactive run was refused. The pass rules were written before the test and the test passed, so the user decided to build layer 2, with the 2026-11-22 cut-off unchanged.

Claude 写，2026-11-17。实测由用户在 Kiro 编辑器和 kiro-cli 里做，Claude 事先写判定规则、事后对照日志和配置文件核对。依据：`docs/易用性改造方案.md` 第 3.1 节；Kiro 文档 `kiro-permissions`（已登记）。

## 1. 环境

| 项 | 值 |
|---|---|
| 测试文件夹 | `D:\agent\kiro\refcov-trial\perm-test`（GIS 模板的副本，不在仓库里）。MCP 服务名改成 `refcov-test`，和正式的 `refcov` 分开 |
| 规则 | 用户级 `~/.kiro/settings/permissions.yaml`，实测前不存在，新建，只有一条：`capability: mcp`，`match: ["refcov-test/check"]`，`effect: ask` |
| 被测工具 | `check`（只读，不写日志）；对照用 `report`（也只读，没有规则） |

| 模型 | claude-haiku-5.5 |

文档的说法（实测前查的）：新建权限文件只是在默认规则上加，不替换；显式的 `ask` 每次都问，不提供 Always allow；优先级 deny > ask > allow > evaluate；Approve for me 只判断没有规则管的动作；`--trust-all-tools` 信任规则没有 deny 的所有动作。

## 2. 判定规则（实测前写下）

第二层做，当且仅当：

- 问题 1：`check` 每次调用都弹窗（第二次也弹），能看到工具名和参数值；
- 问题 2：Approve for me 下仍弹窗（菜单里没有这一项记"不可用"，不算失败）；
- 问题 3：`autoApprove` 含 `check` 时仍弹窗。

问题 4 被绕过不算失败，按文档本来就可能绕过，写进局限。弹窗看不到参数值就不做第二层：用户没法在弹窗里看到实际会执行的内容。

## 3. 结果

| 问题 | 做法 | 观察 | 结论 |
|---|---|---|---|
| 1 | Supervised 模式，先调 `report`（对照），再调两次 `check`，参数 `path` 为 `README.md` | `report` 弹窗，有 Allow、Always allow、Deny、Always deny；按步骤选 Always allow（This session）以后再调，仍弹（用户报告）。`check` 两次都弹；批准框写着 `@refcov-test/check`，它上方的工具卡片显示参数 `{"path": "README.md"}`；批准框只有 Allow、Deny、Always deny，没有 Always allow | 通过 |
| 2 | 同一个聊天切到 Approve for me，调 `check` | 弹窗 | 字面上通过。没有做 `report` 的对照，不能排除判断模型当时不可用（文档：不可用时什么都问） |
| 3 | `autoApprove: ["check"]`，Supervised，调 `check` | 弹窗 | 见下面的对照 B |
| 3 对照 B | `autoApprove: ["check", "report"]`（核对过文件，JSON 合法），重新加载窗口，Accept file changes 模式，各调一次 | `report` 弹（有 Always allow），`check` 弹（没有 Always allow） | `autoApprove` 在这里没起作用，所以没测出它和 `ask` 冲突时谁赢；没有发生绕过。按事先的判读记为通过，带这条说明 |
| 4 | kiro-cli `chat --v3 --no-interactive --require-mcp-startup`，加和不加 `--trust-all-tools` | 加：`check` 不经确认就运行（同一会话还经 MCP 读了 24 个单元，测试文件夹日志可查，所以 `check` 返回"达标"属实）。不加：`[denied] tool permission approval is not supported in non-interactive mode`，并提示可用 `--trust-tools=@refcov-test/check` | 和文档一致：带信任参数就绕过 |

没测到：保存 MCP 配置后 Kiro 会不会自动重连（用户拿不准，后来手动重新加载了窗口）；kiro-cli 交互模式下的弹窗；Kiro 编辑器的版本号。

## 4. 结论

按事先的规则，第 0 步通过。用户 2026-11-17 决定做第二层，11-22 没做完就砍（`docs/易用性改造方案.md` 第 4 节不变）。

对第二层设计有用的几点：

- 弹窗本身只写工具名，参数值在它上方的工具卡片里。所以"弹窗里显示的就是实际会执行的内容"要靠参数来做：写入工具的参数应当就是要执行的内容（文件、哈希、编号），服务端再核对它和提议一致。
- 显式 `ask` 的弹窗不提供 Always allow，用户不会一次点击就把它变成永远放行。
- 问题 3 留下的不确定可以接受：按文档优先级 `ask` 赢过 `allow`；而且第一版只新增参考源、永不缩小必看范围，即使在别的环境里被绕过，最坏的结果是多一份必看材料。
- 命令行带 `--trust-all-tools` 或 `--trust-tools` 时没有确认。第二层的确认只对编辑器和不带这些参数的命令行成立，要写进局限。对外不讲"防蓄意绕过"。

## 5. 收尾

- 测试文件夹 MCP 配置里的 `autoApprove` 一行由用户删掉。
- 用户级权限文件留着；做第二层时，规则改成针对正式服务器的写入工具。
