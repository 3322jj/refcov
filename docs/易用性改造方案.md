# 易用性改造方案（Kiro 版）

EN summary: RefCov works, but installing and using it takes too many manual steps, even for its own developer. This plan, agreed on 2026-11-17 after Claude's assessment and an adversarial review, splits the work in two layers. Layer 1 makes installation simple: package the Kiro hook script and templates, add `refcov init` and `refcov doctor`, and allow installing without keeping a source clone; it goes ahead now. Layer 2 lets Kiro manage reference material in natural language while the user keeps the authority, using Kiro's own permission prompt (`ask` rule on one MCP tool) as the confirmation step; it is built only if a 45-minute hands-on test in Kiro passes, and its first version only adds new Markdown sources through MCP, never shrinks the required set, and never claims to stop deliberate bypass. Layer 2 is dropped if it is not done by 2026-11-22. Claude Code and Codex support are out of scope for this contest.

Claude 写，2026-11-17。依据：用户的改造构想、Claude 的评估（对照代码和 Kiro 官方文档）、一轮反方审查和 Claude 的逐条回应。用户已同意按本文推进。

## 1. 为什么改

RefCov 的核心功能已经成立，但用户要做的事太多：克隆仓库、装 Python 依赖、运行安装脚本、改 `refcov.toml`、在终端登记和同步资料、回 Kiro 重连 MCP。连开发者自己都嫌麻烦。目标是：**装一次；之后像平时一样把参考资料交给 Kiro；只在需要授权时点一下。**

原则不变：**Agent 负责执行，用户负责授权。** 简化不能把"用户明确批准"弱化成"AI 自己调一个登记工具"。

## 2. 第一层：安装简化（直接做）

| 改动 | 说明 |
|---|---|
| 调整打包 | `pyproject.toml` 现在只打包 `refcov*` 和 `refcov_mcp*`，`integrations/kiro/` 里的钩子脚本和模板不在包里。改成随包安装，钩子改用包里的命令 |
| 不保留克隆也能装 | 例如 `uv tool install git+https://github.com/3322jj/refcov` |
| `refcov init` | 在用户项目里写 MCP 配置和 5 个钩子；命令里用可执行程序的绝对路径（现在的 `setup.py` 就是这么做的，避免 Windows 上找不到命令）；不覆盖已有的有效配置 |
| `refcov doctor` | 检查 MCP 配置、5 个钩子、`refcov.toml` 能否解析、已登记资料、待同步、Kiro 权限设置，逐项说明问题和修法 |
| 顺手修一处文档错误 | `setup.py` 生成的 `refcov.toml` 模板里有示例注释 `files = ["videos/*.mp4"]`，照着写会登记失败（登记只收 Markdown；视频要先用镜头应用的 `detect` 生成 `*.shots.md`） |

**验收**（反方审查提出）：

1. 在没有 RefCov 源码克隆的 Windows 环境里能装好。
2. `init` 不覆盖用户已有的有效配置。
3. `doctor` 能发现 MCP、钩子和资料登记里的主要配置问题。

另外核对：Kiro 文档说保存 MCP 配置后会自动重连，"回 Kiro 重连 MCP"这一步可能可以去掉，实测后再写进 README。

## 3. 第二层：自然语言管理资料（先实测，再决定）

### 3.1 第 0 步实测（用户在 Kiro 里做，约 45 分钟，不改仓库）

在用户级权限文件 `~/.kiro/settings/permissions.yaml` 里给现有的只读工具 `refcov/check` 设 `ask`，回答四个问题：

1. 普通 IDE 模式下，是不是每次调用都弹窗；弹窗里显示什么（工具名、参数）。
2. 打开"Approve for me"之后，能不能跳过弹窗。
3. MCP 配置里的 `autoApprove` 和 `ask` 冲突时，谁赢。
4. kiro-cli 加 `--trust-all-tools` 时，能不能绕过。

官方文档写的优先级是 deny > ask > allow > evaluate，权限文件存在用户机器上，克隆下来的仓库注入不了；但第 4 条按文档本来就可能被绕过，所以命令行要另有退路。

**实测不通过**：第二层放进"以后再做"，只交付第一层。

### 3.2 实测通过后做什么（第一版）

- `propose_sources`：分析用户给的资料，生成一份**待批准的提议**，绑定完整的文件哈希和适用范围，不改变必看范围。**第一版只收 Markdown**；视频要先跑 ffmpeg 生成镜头清单、还要声明适配器，放到第二版。
- **只开放一个写入工具** `apply_proposal`，在权限文件里设 `ask`：
  - 必须对应一份已存在的提议，参数和提议逐项一致，弹窗里显示的就是实际会执行的内容；
  - 执行前重新计算文件哈希，不一致就拒绝；
  - 每次执行在日志里记一条。
- **第一版只允许经 MCP 新增参考源。** 已有资料的更新：只有能把具体改动摆给用户看、并重新确认时才走 MCP，做不到就退回终端 `refcov sync`。**删除和缩小必看范围永远不开放给 MCP。** 不能靠单元数量判断"有没有缩小"：一个章节里的五条要求删成一条，单元数可能不变。
- 不把现有的 `sync()` 原样暴露给 MCP：它除了新增和改动，还会处理"文件已不在""已移出配置"两组，等于间接缩小必看范围。
- 资料的变化分开显示两件事：钩子**检测到的 AI 写入操作**（只是参考，钩子看不到 shell 写文件）和**文件哈希比对出的实际变化**（以这个为准）。

### 3.3 对外怎么说

- 可以讲：安装从 7 步变成 2 步；Kiro 正常工作流里，登记新资料由用户在 Kiro 的权限弹窗里批准。
- 不能讲：防蓄意绕过。现在的"只有用户能在终端登记"也拦不住蓄意绕过（保护检查只认几种命令写法，AI 可以写一行 Python 直接调接口），新方案同样如此。
- 要讲清楚的时间窗口：资料**改了并且重新登记之后**，改过的单元的旧读取才失效；改了还没同步时，状态行提示"待同步"，关卡不拦。
