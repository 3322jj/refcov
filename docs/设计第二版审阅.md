## 一、会挡住写代码的

### 一.1 钩子脚本和 MCP 服务怎么找到代码和仓库根目录，设计里没写

设计全文没有出现"工作目录""解释器""安装"这几件事。会出两个问题：

- **钩子脚本 import 不到核心层。** 钩子命令是 `python integrations/kiro/hook.py <事件>`。这样启动时 Python 的搜索路径是 `integrations/kiro/`，不是仓库根目录，`import refcov` 会失败，除非包已经装进这个 `python` 对应的环境。按设计第 8 节第 3 步，import 失败会被当成"自身出错"而放行。结果是关卡无声失效，正是需求 11.4 里写的那种情况，而且是自己造成的。
- **MCP 服务可能把状态目录建在别处。** MCP 服务由 Kiro 的扩展宿主启动（`验证结果.md` 第 6 项），它的工作目录不一定是工作区根目录。如果服务按当前目录找 `.refcov/`，读取记录会写到另一个地方，而钩子（工作目录实测是工作区根目录）看的是仓库里的 `.refcov/`，覆盖率会一直是 0。

改法（都在任务 1 里加一句）：

- 定下用哪个 Python、怎么安装（例如在 PATH 上的那个 Python 里 `pip install -e .`），写进 README。
- `hook.py` 开头按自己的文件位置算出仓库根目录，不依赖当前目录。
- MCP 服务用启动参数接收仓库根目录，`docs/mcp.example.json` 里写出这个参数。
- 任务 6 的完成标志加一条：`.refcov/errors.log` 是空的。

### 一.2 `refcov add` 放行的理由不成立

设计第 6 节和第 11 节说：AI 用 shell 重新登记"只会让旧记录失效，覆盖率只会变低"，所以放行。

这只在重新登记同一份内容时成立。AI 可以用**同一个参考源 ID 登记另一个很小的文件**（例如 `refcov add empty.md --id kiro-hooks`）。这个参考源变成只有一个单元，读一下就是 100%，关卡放行。

这也偏离了冻结的需求 14.4（"其他会写记录的 RefCov 入口"要拦）。任务 9 本来就写的是"由用户在终端登记"，AI 并不需要这个命令。

改法：把 `add` 加进 `USER_ONLY`。改动是元组里多一个词、任务 14 的测试里把"`refcov add` 放行"改成"被拦"，同时消掉一处"偏离需求原文"。

### 一.3 写入后记录的去重和实测对不上（设计第 8 节 `refcov-file-save.json`，任务 17）

设计：PostFileSave 触发时，"10 秒内同一路径已有 `write` 记录就跳过，否则记来源不明"。

问题有三个：

- 按设计第 6 节，`record_write` 只在"不达标、无法判断、来源不明"时才追加 `write` 记录。所以**达标时的每一次正常写入都没有记录可比**，PostFileSave 会把它们全部记成"来源不明"。
- PostFileSave 和 PostToolUse 是两个进程，几乎同时触发（`hooks.jsonl` 里 20:34:54 的三条），谁先写日志不确定。PostFileSave 先到时同样会多记一条。
- 实测里用户手动保存**没有**触发 PostFileSave（DEVLOG 第 406 行，只测了一次），触发的都是 AI 写入。也就是说，这个钩子目前看到的每一次保存，PostToolUse 都已经处理过了。

改法：先测一件事，AI 用 shell 写文件（例如 `Set-Content`）时 PostFileSave 触不触发。

- 不触发：这个钩子没有任何新信息，删掉 `refcov-file-save.json` 和对应分支。需求 10.3 是"收到保存事件时"才适用的条件句，不注册这个钩子不违反它。
- 触发：它是唯一能发现 shell 写入的地方，值得留。但去重要改成：PostToolUse 每次写入都记一条（含达标的），"来源不明"在生成报告时判断（同一路径前后 10 秒内没有写文件工具的记录才算），不在钩子里判断。这样和先后顺序无关。

### 一.4 shell 文本匹配会拦住这个项目自己的日常开发（设计第 8 节第 2 步，任务 14）

匹配词里有 `integrations/kiro`、`refcov_mcp`、`.refcov`。它们是这个仓库自己的源码目录和状态目录的名字，任务 14 上线后，Kiro 开发本项目时下面这些命令都会被拦：

- `git add integrations/kiro/hook.py`、`git diff integrations/kiro/…`
- `git add .refcov/sources.json`（清单是要提交的）
- 任何文件名带 `refcov_mcp` 的测试，例如 `pytest tests/test_refcov_mcp.py`
- 用管道喂 stdin 本地自测钩子脚本（Kiro 一直用这个办法）

设计里提到了"会拦住读状态目录和提交信息"，但没意识到会拦到自己的源码路径。

改法：`integrations/kiro` 和 `refcov_mcp` 这两个词只在**被执行**时才匹配，不是出现就匹配。例如匹配"`python … hook.py`"和"`-m refcov_mcp`"。`.refcov` 和 `refcov.toml` 保持出现就拦，README 里写明提交清单要用 `git add -A` 或由用户提交。

### 一.5 保护检查写错一行，Kiro 会把自己锁死

需求 14.5 要求保护检查出异常时拦截。任务 14 上线后，如果这一步有个小毛病（例如取字段时出异常），**每一次写文件和每一条 shell 命令都会被拦**，Kiro 既改不了 `hook.py`，也跑不了命令，只能由用户出手。

不用改设计。在任务 14 里加一句逃生办法并写进 README：用户把 `.kiro/hooks/refcov-pre-*.json` 移走即可立即停用（DEVLOG 第 433 行实测过移走立即生效）。

### 一.6 `refcov init` 在核心层里写死了接入层的路径

设计第 6 节：`init` 从 `integrations/kiro/refcov.example.toml` 复制配置。`init` 属于核心层的命令行，这等于核心层知道了 Kiro 接入层在哪，和需求 13.1 的意图不一致。另外任务 15 的完成标志需要 `refcov.toml` 里有 `[[scope]]`，而 `init` 排在任务 16。

改法见三.1：砍掉 `init`。

### 一.7 "和上一次报告比"的标红只会出现一次（设计 3.6）

`watch` 组的基准是 `.refcov/report-last.json`，"每次生成报告时"更新。UserPromptSubmit 每条消息都会生成一次报告。所以钩子文件被改之后，标红只在下一条消息里出现一次，再下一条就成了新基准。

改法：只有用户在终端跑 `refcov report` 时才更新基准，钩子和 MCP 生成的报告只比较、不更新。如果采纳三.1 把任务 16 推后，这条也一起推后。

### 一.8 小处，写代码时顺手定下来

| 位置 | 问题 | 改法 |
| --- | --- | --- |
| 设计第 5 节 | `read_unit` 的返回"末尾一行是 `refcov-call:`"，又说每个工具的返回都带一句提示。两句谁在最后没写；单元正文里也可能恰好有一行 `refcov-call:` | 提示在前，`refcov-call:` 永远是最后一行；钩子只认最后一行 |
| 设计 3.2 | 哈希按"上一行原文"算，没说含不含换行。日志要提交，Windows 上 git 可能把换行转成 CRLF，换一台机器校验就会报断链 | 按不含换行符的 UTF-8 内容算；写文件时固定用 `\n`；加一行 `.gitattributes` 让 `*.jsonl` 不做换行转换 |

## 三、可以砍或推后的

按评分看，骨架里评委看得见的只有四样：读取记录的回放、写文件被拦、任务开工被拦、出处报告。其余都是幕后的东西。

| # | 砍什么 / 推后什么 | 理由 | 大约省下 |
| --- | --- | --- | --- |
| 三.1 | **任务 16 整个标成可选；其中 `init` 直接砍掉** | `init` 只是复制一个文件、建一个目录，README 里写一行让用户自己复制就行，状态目录在第一次写入时自动建。砍掉它同时解决一.6，`USER_ONLY` 也只剩 `confirm` 和 `add`。`confirm` 和文件校验值评委看不到，两个应用也用不到，做完应用再回来做 | 大半天 |
| 三.2 | **任务 18（任务开工关卡）从可选改成必做，和任务 16 对调** | 这是最"Kiro"的一个关卡：用户在规格界面点 Start task，被拦，原因直接显示在 IDE 里（`验证结果.md` 第 5 项已实测）。它比写文件被拦更适合放进视频，也是"Kiro 技术"这一项的实证。现在它是可选，而评委看不到的任务 16 是必做，优先级反了 | 不省时间，换来演示素材 |
| 三.3 | **任务 17 的 PostFileSave 分支** | 见一.3。实测如果是"shell 写入不触发"，整个分支和一个钩子文件都可以删 | 两三个小时 |
| 三.4 | **任务 19（凭证）放到最后，时间不够就不做** | 需求 7.5 已经规定凭证不参与任何拦截，它只是一条记录。`check` 工具已经能回答"我达标了吗"。对演示和评分都没有贡献 | 半天 |
| 三.5 | **报告里的 `tokens`、`files` 两栏随对应任务推后** | 任务 7、11 不用为还没做的功能留实现 | 小 |

不建议砍的：属性测试（任务 12）、Linux 持续集成、轻量模式的那两条性质。它们成本小，而且是"Kiro 技术"的直接证据。
