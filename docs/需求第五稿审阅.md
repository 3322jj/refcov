## A. 矛盾、重复、做不到

### A1. "主关卡不依赖钩子"说过头了（需求 7 用户故事、7.6）

凭证由 MCP 服务发，但 MCP 服务拦不住 Kiro 自带的写文件工具。没有钩子时，没人检查凭证，写入照常发生。所以：

- 凭证本身是"协作式"的：它告诉 AI 还差什么，给审计留快照，但不拦任何东西。
- 真正能拦的只有钩子（第 2 层）。事后记录（第 3 层）也要靠钩子才能知道发生了写入。

这一条源自我早先的建议，是我说得不严谨。改法：把需求 7 的用户故事改成"让核心层给出与工具无关的达标判断和凭证，接入层据此拦截"；7.6 改成"凭证的发放和判断不依赖钩子；拦截依赖接入层"。对外材料里不要写"换了别的工具关卡也还在"。

### A2. 拦两次后第三次放行，等于关卡可以硬闯（需求 11.2）

AI 把同一次写入重试三遍就过了，什么都不用读。被拦后重试正是 AI 的常见反应。这条也源自我早先的建议（当时参考的是"回答结束时拦截"的同类项目，那种场景有死循环风险；写文件前拦截没有这个问题，因为 AI 永远有路可走：去读）。

改法：删掉自动放行。拦到第 2 次起，原因里加一句"停下来，向用户说明情况"。用户想放行，自己把 `enforce` 改成 `false`（需求 17.1 已有，且只有用户能改）。这样还能删掉术语"同一件事"、报告里的"超过拦截上限后放行"两处内容。

### A3. 放宽项和"被引用的单元必看"打架（需求 5.3 对 6.5、16.3）

用户放宽了单元 X（5.3 说两种模式都移出必看集合），但某条需求引用了 X 且没读过。6.5 和性质 16.3 说一定不达标，5.1 末尾又说"再按放宽项调整"。两边对不上。

改法：写明一条规则，"被需求引用的单元永远必看，放宽项不能移除它们"。

### A4. 申请凭证时不知道是为哪个路径申请（需求 7.1、8.1、9.1）

8.1 说达标判断按"目标路径 → 参考源"的对应关系做，9.1 说要有"覆盖该路径的有效凭证"，但 7.1 的申请动作里没有路径或范围这个参数。第四稿的"申请凭证要报任务"在第五稿删了，这个缺口随之出现。

改法二选一：申请时带上范围规则的名字，凭证记下自己覆盖哪条规则；或者凭证不分范围，由钩子在写入时按路径找到规则、现算是否达标。后者更简单。

### A5. 改了需求里的引用，旧凭证还有效（需求 7.4、7.5）

拿到凭证后，往需求文档里加一条引用，指向一个没读过的可选单元。按 6.5 这时已不达标，但 7.4 的失效条件里没有这一条，7.5 又规定写文件只认凭证。任务开工检查（9.6）能补上，写文件关卡补不上。

改法：7.4 加一条失效条件，"需求文档引用的单元集合变了"。如果采用 A4 的"钩子现算"，这个问题自然消失。

### A6. 幻影需求和无效引用只列出、不影响达标（需求 6.2、6.4）

"需求必须标出处"是和同类项目拉开差距的核心，但现在两种模式下都只是报告里的一行。AI 可以一条出处都不标，照样拿凭证。

要定的事：严格模式下，存在幻影需求或无效引用是否判定不达标。同时要先解决 `citation.md` 的待定问题 3：用户口头或聊天里给的要求算不算出处。不解决的话，凡是来自对话的需求都会变成幻影需求。建议设一种明确的出处类型表示"用户指示"，并要求附上原话或日期。

### A7. 两份引导文档互相矛盾（citation.md 对 testing.md）

`citation.md` 的正则 `\[ref:([a-z0-9-]+)/([^\]\s]+)\]` 不允许单元 ID 里有空格。`testing.md` 要求测试数据里"单元 ID、标题要包含中文、空格、特殊字符"。

改法：ID 限定为不含空格和方括号的字符；标题不限。测试约定里把"ID 含空格"去掉，改成验证这类 ID 会被拒绝。

### A8. 单元 ID 的生成方式会影响引用是否悄悄指错（需求 2.5，citation.md 待定问题 1）

如果用序号（`sec-03`），文档开头插入一节后，所有序号后移，需求里的 `[ref:…/sec-03]` 会悄悄指向另一段内容，程序不会报错。建议用标题生成的短名，重名时加后缀。标题改了引用会变成无效引用，这是看得见的错误，比悄悄指错好。

### 威胁模型（B1 的根本问题）

AI 有 shell，就能读写磁盘上任何文件。在这个前提下，防不住蓄意造假，只能做到两点：

1. 防住"顺手偷懒"和无意的破坏。
2. 让篡改留下痕迹。

建议在需求 11.4 或 14 里明写这句话："本工具防的是偷懒和虚报，不防蓄意伪造记录的 AI。"然后做两件便宜的事：

- shell 命令文本里出现状态目录路径或配置文件名时拦截（接入层，文本匹配，会有漏网）。
- 读取记录做成哈希链：每条记录带上一条的校验值。报告里显示链是否完整。它不能阻止有心的伪造，但能让随手追加或改动立刻暴露。

写明威胁模型之后，需求 14 不需要再往上加码。

### 会话归属（B6，可能有更准的办法）

`验证结果.md` 第 6 项的结论是 MCP 服务拿不到会话 ID，所以第五稿改成了不按会话判断。但我在 `kirohe` 的钩子日志里看到：调用 MCP 工具时，PreToolUse 和 PostToolUse 钩子都触发了，钩子输入里有准确的 `session_id`、工具名和参数（15:40:45 的 `mcp_refcov_image_test_get_test_image` 有一条 pre 记录，15:40:49 有一条带 `tool_response` 的 post 记录）。

所以可以这样做：读取记录仍由 MCP 服务写，同时让接入层给 RefCov 的读取工具挂一个 PostToolUse 钩子，由钩子把准确的会话 ID 补记上去。这样：

- 不再需要"当前会话"文件（4.5），两个会话交替也不会记错。
- 报告可以同时给出"本会话看过"和"历史上看过"两个数。
- 需求 17.3 的按会话统计才可靠。

**这一点只看到过一次日志记录，需要专门实测**：MCP 工具的 PostToolUse 是否每次都触发，钩子输入里的参数是否完整。

是否恢复"按会话判断"是用户的决定。最低限度的建议是：判断仍然不分会话，但 UserPromptSubmit 的那一行和报告里要把两个数都显示出来，例如"本会话 0/31，历史 31/31"。否则演示"AI 没看就动手"时，只要之前的会话读过，工具会显示 100%，和要演示的事正好相反。

## C. 精简：可以砍的

规则对这个类别的原话是骨架要"精简到清楚"。现在骨架一个规格就有 89 条细则。

| # | 砍什么 | 涉及条文 | 理由 | 省下 |
| --- | --- | --- | --- | --- |
| C1 | 第三次自动放行 | 11.2、术语"同一件事"、12.2 两项 | 见 A2 | 小，但同时堵一个洞 |
| C2 | shell 受控命令关卡 | 9.2、9.3、9.4 | 写文件钩子已实测可用，这一层的必要性下降；文本匹配漏洞多，白名单解析复杂。保留 14 里对状态目录的文本匹配即可 | 中 |
| C3 | 分页读取 | 4.2 | 改成拆单元时限制单元大小，超长的拆成多个单元。不需要记"哪几页读过" | 中 |
| C4 | 轻量模式（移到"应该有"或"以后再做"） | 需求 15、2.2–2.4 的关键类型、5.2、12.2 的"本模式未要求"、16.5、16.6、17 的第三组 | 一个模式变两个，状态和测试都翻倍。放宽项（5.3）和范围规则（需求 8）已经能手动缩小必看集合。对照实验用开、关两组就够 | **大** |
| C5 | Linux 支持降为"持续集成里跑测试" | 13.5 | 没有 Linux 用户场景，不值得专门调试 | 小 |
| C6 | 报告字段 | 12.2、12.3 | JSON 是唯一数据源，文字版由它生成。砍掉 C1、C4 相关字段 | 小 |

## D. 按评分标准，最大的风险

### D1. 时间都花在地基上（影响全部五项）

第一天出了五稿需求、五份引导文档、一个自定义 agent，没有一行产品代码。这些是很好的"Kiro 用得深"的证据，但评分里设计、展示、真实用途合计 60%，靠的是两个应用、在线演示页和视频，这些都还没有规格。

建议：需求到此冻结，只改本文 A、B 里点名的条文。设计和任务阶段先做一条最细的通路：登记一份 Markdown → 拆单元 → 经 MCP 读 → 记录 → 报告。这条通路两天内跑通，然后立刻用它管 Kiro 自己读规则页和钩子文档。关卡在这之后再加。这样"工具管住了开发它的 AI"的记录才能尽早开始积累。

### D2. 仓库里几乎全是中文（影响"Kiro 技术"和第一轮筛选）

规则要求提交材料用英文或附英文翻译。评委评"Kiro 用得怎么样"时会翻 `.kiro` 目录，评审还可能有自动分析。现在需求文档、引导文档、agent 配置全是中文，只有 DEVLOG 的后半部分带了英文行。

建议现在就定规矩，越晚补越贵：

- 根目录放英文 README（现在没有 README）。
- 每条需求的标题和用户故事下加一行英文；或另存一份英文版规格，并在引导文档里规定两份同步。
- 引导文档开头加几行英文摘要。

### D3. 类别是否切题（第一轮是及格线）

评委要看到的是"一个精简的骨架 + 两个明显不同的应用"。现在的骨架更像一个完整产品，两个应用在文字里只是"两个适配器"。

建议：两个应用各自要有独立的页面、独立的演示数据、独立的可运行入口，放在两个文件夹。对外第一句话讲"适配器接口只有三个函数，文档适配器 50 行"，再讲关卡。

### D4. 说过头的话（影响"真实用途"的可信度）

"不准写文件""换工具关卡也还在""AI 只能经工具取材料"这三句都比实际强（见 A1、A2、B4）。评委是工程师，会追问。对外统一成做得到的说法：记录是否看过、算出覆盖率、在 Kiro 里拦住自带写文件工具和任务开工、其余情况事后标红。

### D5. 公开仓库里有一个邮箱地址

`docs/DEVLOG.md` 第 97 行写出了第一次提交用的姓名和 Gmail 地址，还写了旧提交的哈希。当时改提交作者就是为了不公开这个邮箱，但这段文字又把它公开了。建议把邮箱从 DEVLOG 里删掉（改成"用了个人邮箱"）。注意它已经在提交历史里，要彻底去掉需要改写历史并强制推送，这一步由用户决定。

### D6. 还没用上的 Kiro 功能

- **Analyze Requirements**：Kiro 自带的需求分析正是查矛盾和歧义的。DEVLOG 里没有运行它的记录。建议现在对第五稿跑一次，把它查出的问题和本文 A 节对照，结果记进 DEVLOG。这既能查漏，也是一条很好的使用记录。
- 属性测试、power、Crew 都还没开始，属正常进度。

## 建议的处理顺序

1. 删邮箱（D5），加英文 README 和双语规矩（D2）。
2. 对第五稿跑一次 Analyze Requirements（D6）。
3. 用户拍板四件事：A2（取消自动放行）、A6（幻影需求是否影响达标、用户指示怎么算出处）、B6（是否显示或恢复按会话）、C4（轻量模式是否推后）。
4. 按 A1–A9、B1–B2 改条文，砍 C1–C3、C5–C6。不出完整的第六稿，改动记进 DEVLOG。
5. 实测一项：MCP 工具的 PostToolUse 钩子是否稳定触发并带会话 ID。
6. 进入设计阶段，先做 D1 说的那条最细通路。
