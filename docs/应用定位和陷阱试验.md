# 两个应用的定位、证据和演示（第二版）

EN summary: Second version (2026-11-14), replacing the trap-trial plan. Strong models read small or explicitly named material (6 of 6 GIS runs correct), so the "set a trap, watch the AI fail" demo is dropped. RefCov's pitch becomes split, read, gate: it splits material into units so an agent can read all of it cheaply and on record, and blocks writes when the agent's "I know enough" is wrong. The shot-coverage app carries the main evidence (a 7-minute reference video: without RefCov, 30 minutes and 88 tool calls with no output); the layer-coverage app shows requirement traceability in Kiro's spec workflow.

Claude 写，用户 2026-11-14 同意。第一版（陷阱试验计划）在提交 `99c2692`，试验经过和数字在 DEVLOG 2026-11-13 夜一节。

## 1. 结论

- **卖点：拆、读、拦。** RefCov 把参考材料拆成单元，让 AI 能完整、便宜、有记录地读完；它觉得"懂了"但其实没读够的时候，拦住它。
- **镜头覆盖率（视频）证明"拆和读"**，承担主要证据：大材料读全，又快又省。
- **图层覆盖率（GIS）证明"拦和出处"**：Kiro 规格里的每条需求都能追到材料。
- "设陷阱等 AI 出错"的试验结束，不再做正式的 10 + 10。

## 2. 为什么改：这两天的四个发现

1. **材料小、或读材料就是任务本身时，强模型会认真读。** 纽约建筑轮廓的陷阱题，claude-sonnet-5.5 点名字典时 3 次全对，不点名、只在 README 里指向 `docs/` 时也 3 次全对（每次都顺着 README 找到并只打开了对的那份字典）。deepseek-3.2 也读了。
2. **材料只是手段、会话长、手上忙别的事时，强模型会凭印象办事。** 例子：Claude 在这个项目里两次没读手边的材料就下结论（没打开规则就建议"两个应用降成一个"；没读 `docs/验证结果.md` 就把"MCP 图片能不能送达"列成未验证）。Hermes Agent 的 issue #124875 是同类：指令里写满了"必须读完"，照样跳过。
3. **材料大到读一遍很贵时，强模型可能不是偷懒，而是花不起。** 7 分 40 秒的参考视频（EP01），Sonnet 不装 RefCov：三档灵敏度切镜头、查 OCR 工具、看了 70 次图片、写脚本测转场时间，88 次工具调用，30 分钟超时，没有交出结果（`D:\agent\kiro\refcov-trial\runs\20261114-002344\V-01`，日志在 `logs\` 同名目录）。它是在现场重新发明一个镜头切分工具。
4. **关卡本身好用。** CLI 里 qwen3-coder-next 不读就写，被拦，照拦截原因经 MCP 读完 7 个单元，再写就放行（`gate-check\20261113-225732\`）。

第 1 条说明我们之前的试验一直在考"读材料的题"；第 2、3 条才是 RefCov 真正有用的场景。

## 3. 对外讲法

一句话：**AI 读了多少参考材料，应该是一个数字，而不是一句"我看过了"。**

- **拆**：视频按镜头、数据按字段、文档按章节，拆成单元。AI 不用自己发明切分工具。
- **读**：一个单元经 MCP 读一次记一笔。读全变得便宜，读了多少一目了然。
- **拦**：AI 判断"够了"但其实没读够时，Kiro 钩子拦住写文件和任务开工。

照实说清适用条件：小材料、点名时，强模型本来就会读，RefCov 只多一份记录；材料大、贵、是手段而不是任务本身时，RefCov 的价值最大。

不说：RefCov 能防蓄意伪造；AI 只能经工具取材料；shell 写的文件也拦得住（实测拦不住，见 `docs/验证结果.md` 第 8 项）。

## 4. 镜头覆盖率 `apps/shot-coverage`：拆和读

### 要做的

- **镜头适配器**：用 ffmpeg 场景检测把视频切成镜头单元。每个单元：起止时间、一张关键帧（必要时首尾各一张）。单元 ID 按时间码。
- **骨架要补一处（检查点 3，要先停下等审阅）**：适配器接口已经能返回图片（`refcov/sources.py` 的 `Image`），但 `api.read` 现在只返回文字、读取记录的 `images` 写死为 0，MCP 的 `read_unit` 也只返回字符串。要让 `read_unit` 把关键帧作为图片送出去，读取记录里记下图片张数。
- **页面**：镜头条，读过的亮、没读的灰（和第 7 节的视觉语言一致）。
- 不做：理解画面内容的模型、剪辑功能。

### 对比试验（主要证据）

- 材料：EP01 的隔离副本 `D:\agent\kiro\refcov-trial\materials\video-ep01\reference.mp4`（用户自己的作品）。注意画面里有真实公司名字，进参赛视频或演示页时只能用没有这些字的镜头。
- **任务改成"用材料做事"，不再是"读材料的题"**。示意（英文定稿时再改）："照 reference.mp4 的节奏、转场方式和画面文字风格，为一个新主题写一份 30 秒的剪辑方案 edit-plan.md。方案前列出你借鉴的手法，每条写上它在参考视频里出现的时间。"
- 两组：不装 RefCov；装 RefCov（镜头适配器 + MCP + 钩子，写 `edit-plan.md` 前要读完全部镜头）。同一模型 claude-sonnet-5.5。
- 记：有没有交出结果、用时、额度、看了多少镜头（装了的一组看 RefCov 日志，没装的一组看它抽了多少帧）、借鉴手法写的时间对不对（对照 `film.py` 整理的标准答案）、有没有编出来的手法或时间。
- 每次运行把临时目录也设在运行文件夹里面（V-01 用了系统临时目录，三次共用，后面的运行被污染）。"碰到外部路径就作废"只针对：原工程 `D:\agent\claude`、判分目录 `refcov-trial-grader`、别的运行文件夹、素材目录。
- 不装的一组已有 V-01 一次（超时、没交卷）可作参考，但它的任务是逐镜表，和新任务不同，正式对比要重跑。
- 判定规则和次数在跑之前写进 DEVLOG，跑完不改。

## 5. 图层覆盖率 `apps/layer-coverage`：拦和出处

- 数据：纽约建筑轮廓（NYC Open Data `5zhs-2jue`），演示用 Bayside 子集；数据字典是官方 Markdown（见附录）。
- **图层适配器**：把每个字段做成一个单元，"数据文件里看到的"（字段名、类型、取值分布）和"数据字典里写的"（含义、单位、编码表）合在一起。另有坐标系、范围单元。否则和文档适配器分不开。
- 演示的是 Kiro 规格流程：AI 根据数据和字典写需求，每条需求用 `[ref:…]` 标出处；没出处的被列成幻影需求；引用了没读的字段单元，写设计和代码时被拦。
- **证据看 B 线**：B2 × 3 已跑完（不装 RefCov，Sonnet 根据字典写需求，要求每条写明出自哪一节），三份原样在 `D:\agent\kiro\refcov-trial\B2-review-20261113\`，**由 Claude 逐条判**：有没有材料里没有的需求；这些需求有没有被随手标上出处。后者决定出处检查能抓住多少。

## 7. 视觉语言

一排单元格子：读过的亮、没读的灰、被需求引用的带标记。镜头应用里是镜头条，图层应用里是字段表，演示页随日志回放一格格亮起，视频开场也用它。只做这一个，做精。

## 8. 视频分镜（3 分钟以内，英文）

1. **开场，约 20 秒**：一个 7 分钟的参考视频交给 AI。不装 RefCov：30 分钟、88 次工具调用、70 张图，没有交出东西。
2. **拆，约 25 秒**：同一个视频被拆成几十个镜头单元，镜头条全灰。
3. **读和拦，约 45 秒**：AI 一个镜头一个镜头地读，格子逐个亮起；没读完就想写方案，被拦；读完放行，方案里每条手法都标着镜头。旁边是两组的用时和额度。
4. **出处，约 40 秒**：GIS 规格里每条需求标着字段单元；一条没出处的被标成幻影需求；引用了没读的字段，写代码被拦。
5. **自举，约 25 秒**："我们用 RefCov 管着 Kiro 开发 RefCov"，日志回放；照实给出数字。
6. **骨架和收尾，约 25 秒**：一个核心层，两个适配器各多少行；规格、钩子、MCP、引导文档各一个镜头。

不许出现第三方商标和受版权保护的内容。数字以试验实际结果为准，没测到的不说。

## 9. 风险和待验证

1. **MCP 图片在 CLI 里能不能送达。** IDE 里验证过（`docs/验证结果.md` 第 4 项），CLI 里没测，而对比试验在 CLI 里跑。最先测，很便宜。
2. **骨架补图片返回要动核心层。** 改动不大，但核心层已冻结，按冲刺计划第 3 节第 3 个检查点先停下等审阅。
3. **装了 RefCov 的一组不一定更快。** 如果 AI 照样自己跑 ffmpeg 而不用 MCP，或者读几十张关键帧本身也很贵，结论可能是"更全但不更快"。照实报告。
4. **B2 的结论可能是"AI 写需求很规矩"。** 那图层应用就只讲机制（出处检查和关卡怎么运作），不讲"抓到了多少"。
5. **EP01 里有真实公司名字**，进对外材料时要挑镜头或换素材。
