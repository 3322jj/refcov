# 两个应用的定位、演示画面和陷阱试验

2026-11-12，Claude 写，用户定方向。2026-11-13 按第 0 步的实测改了第 4、5 节。这份文档定方向，不是规格；规格由 Kiro 按它另写。

## 1. 结论

- 两个应用不是两个查看器，是两个"陷阱"：各有一些单元，AI 不看就会做出错的结果。
- **图层覆盖率（GIS）做主线，做透**。它负责证明"不看会出错"，对照实验只做它。
- **镜头覆盖率（视频）做轻，放开场**。它负责让人几秒内看懂"覆盖率"是什么。
- 主陷阱不用坐标系。用"数据文件里看不出来、只有读了说明才知道"的那一类。
- 动手做应用之前，先做第 5 节的试验。试验不通过，主线要重想。

## 2. 两个应用各自的角色

| | 图层覆盖率 `apps/layer-coverage` | 镜头覆盖率 `apps/shot-coverage` |
|---|---|---|
| 角色 | 证据 | 画面 |
| 深度 | 做透 | 能跑、明显不同、有独立入口 |
| 单元 | 图层的坐标系、范围、每个字段（文件里看到的 + 数据字典里写的） | 一个镜头：关键帧、时长、台词 |
| 不看会怎样 | 数字错，而且看起来正常 | 漏掉后面的镜头 |
| 对错 | 有标准答案，能数 | 主观 |
| 对应评分 | 真实用途、创新 | 设计、展示 |

规则只要求两个明显不同的应用、各占一个文件夹，没有要求一样深。但两个都必须真的能跑，和视频里展示的一致。

## 3. 主陷阱怎么选

坐标系不合适，原因有两个：太常见；而且坐标系存在数据文件里，AI 用常见的库一打开就看得到，多半会主动查，陷阱不触发。

好陷阱的条件：

1. 数据文件本身看不出来，只有随附的说明文档里写了。
2. 错的结果看起来正常。结果离谱的话 AI 自己会起疑去查，对照实验拉不开差距。
3. 不懂 GIS 的程序员也能一句话听懂。
4. 有标准答案，能判对错。

## 4. 数据集：纽约市建筑轮廓（NYC Building Footprints）

选它的理由：官方数据字典本身就是一个 Markdown 文件，现有的文档适配器直接能登记；陷阱是数据本来就有的，不是编的。

### 数据字典（2026-11-12 读原文核实）

- 地址：<https://github.com/CityOfNewYork/nyc-geo-metadata/blob/main/Metadata/Metadata_BuildingFootprints.md>
  - 原始文件约 13 KB，按 `text/plain` 提供，路径以 `.md` 结尾，符合 `refcov add <网址>` 现在接受的条件。
  - 所在仓库的许可证是 Apache-2.0。
- 字典里写明的、数据文件里看不出来的事：
  - 要素类型：不是每条记录都是建筑。2100 是建筑，**5110 是车库**，5100 在建，另有加油站顶棚、储罐、附属和临时构筑物、占位三角形等。数据里只有数字代码。
  - 屋顶高度：单位是**英尺**，是高出地面的高度，不是海拔。
  - 建成年份、屋顶高度为 0 或空表示不详；建筑编号不唯一。
  - 坐标系：原生是 EPSG:2263（单位英尺）；不同下载渠道给的是 3857 或 4326。
- 使用限制：元数据写"Open Data policies and restrictions apply"，访问权限是 Public。

### 实际数据（2026-11-13 第 0 步，Kiro 数的）

数据集是 NYC Open Data 的 `5zhs-2jue`，全市 1,082,972 条。

| 项目 | Park Slope | Bayside | Great Kills | 全市 |
|---|---|---|---|---|
| 总条数 | 6611 | 6018 | 4843 | 1,082,972 |
| 5110 车库 | 1.5% | **28.5%** | 8.7% | 19.7% |
| 其他非建筑（储罐、顶棚、占位三角形等） | 2 条 | 1 条 | 1 条 | 662 条 |
| 建成年份为 0 | 0 | 0 | 0 | **0**（不详的全是空值，约 0.9%） |
| 屋顶高度为 0 | 5 条 | 0 | 5 条 | 0.07% |
| 重复的建筑编号 | 0 | 1 个 | 0 | 3 个 |

结论：

- **字典写的"0 或空"在实际数据里只有空值。** 常见的库会自动跳过空值，所以"年份为 0 被当成老建筑""高度为 0 拉低平均值"这两个陷阱不成立。原先第 5 节以建成年份为头号陷阱，是没核实前按字典推的，已放弃。
- **能用的只有两处：车库编码和高度单位。** 车库在 Bayside 约占三成。
- 接口返回的字段名和字典不同（字典 `FEAT_CODE`，接口 `feature_code`；`HEIGHTROOF` 对 `height_roof` 等），取值的大小写也有出入。不当陷阱，演示里可以提一句：真实数据和说明对不上是常态。

### 还没核实

- **能不能把裁出来的数据放进公开仓库。** NYC.gov 的使用条款全文没读。现在的做法：仓库里不放数据，只放下载脚本和数据字典的登记，注明来源。

### 备选

纽约市地块数据 PLUTO：建成年份为空或 0 表示不详，但实际有没有 0 没数过；数据字典是 PDF，现在没有适配器。只在第 5 节的试验不通过时才考虑。

## 5. 先做的试验：不装 RefCov，AI 会不会掉进去

目的：确认陷阱真的会触发。不触发的话，对照实验没有差别可讲。

### 第 0 步：数一遍数据（2026-11-13 完成）

结果见第 4 节。选定 **Queens 的 Bayside**（6018 条）。

### 第 1 步：定一个问题

> 这个街区排除车库后有多少栋建筑？平均屋顶高度是多少米？

两处陷阱，都是"数据文件里看不出来、只有字典里写了"，而且错了结果仍然像样：

1. **车库是编码。** 数据里只有 `feature_code` 的数字，哪个代表车库只有字典写了。猜错或不排除，数量和平均高度都会偏，但看起来正常。
2. **高度单位是英尺。** 当成米，结果大三倍多；但 9 和 30 都像是合理的楼高。

问题里明确说"排除车库"，是为了让答案没有争议：如果只问"有多少栋建筑"，车库算不算建筑本身就说不清，评委可以说是题目含糊，不是 AI 没读材料。

标准答案用脚本按字典算出来：排除 5110 后的条数；高度只取非空且大于 0 的，英尺乘 0.3048 换成米。先写好。

### 第 2 步：跑

- 工作区里放 Bayside 的数据和数据字典（Markdown 原文），提示词里说明"数据说明在某某文件"，和真实用户给材料的方式一样。不装 RefCov 的钩子和 MCP。
- 同一个问题跑 10 次，每次新开会话。
- 每次记三样：有没有打开数据字典；答案；两处陷阱各对没对。

风险：AI 可能凭常识知道纽约的数据用英尺，也可能看几何形状猜出哪个代码是车库。所以要跑出来才算数。

### 判定

- 10 次里至少 4 次有至少一处错：陷阱成立，照这个做主线。
- 只有 1 到 3 次错：换问法再试一轮。
- 一次都不错：考虑第 4 节的备选，或者回来重想 GIS 这条主线。

门槛是我定的，没有依据，可以调。

这个试验交给 Kiro 或便宜的模型跑，不用 Claude。

## 6. 视频里该出现的画面（3 分钟以内）

1. **开场，约 20 秒**：AI 说"参考材料我都看过了"，旁边是记录：12 个镜头只取了 3 个。
2. **镜头覆盖率，约 30 秒**：镜头条 3 格亮、9 格灰。AI 写文件被拦，原因里列出没看的镜头。读完，整条亮起，放行。
3. **图层覆盖率，约 60 秒**（主线）：
   - 不装 RefCov：AI 直接写脚本，给出一个像样的数字。旁边是标准答案，差了多少。
   - 装了 RefCov：写文件被拦，原因点名"要素类型"这个字段单元（车库的代码在里面）。AI 读了，需求里标上出处，结果和标准答案一致。
   - 一条没标出处的需求被列为幻影需求。
4. **对照数字，约 30 秒**：同一个问题，装和不装各跑若干次，各对了几次。
5. **骨架，约 30 秒**：适配器接口有几个函数，两个适配器各多少行；规格、钩子、MCP、引导文档各一个镜头。
6. **收尾，约 10 秒**。

不许出现第三方商标和受版权保护的内容。

## 7. 镜头覆盖率做到哪一步

- 一个适配器：把一段视频按镜头切成单元，每个单元有关键帧、起止时间、台词。
- 一段演示视频：用户自己拍的。
- 一个页面：镜头条，看过的亮、没看的灰。
- 一次真实会话的记录，演示页能回放。

不做：理解镜头内容的模型、剪辑功能。

## 8. 风险，按先后排

1. **第 5 节的试验结果。** 最先做，决定主线成不成立。
2. **MCP 返回的图片，Kiro 的模型看不看得到。** `docs/验证结果.md` 测过 MCP 图片，结论要对一下。看不到的话，镜头单元只能退成文字。
3. **数据能不能放进公开仓库。** 见第 4 节。
4. **字段单元怎么来。** 数据字典里所有字段在同一个表格里，文档适配器会把整张表切成一个单元。图层适配器要自己把每个字段做成一个单元，把"文件里看到的"和"字典里写的"合在一起。这是图层应用规格里要定的第一件事。
