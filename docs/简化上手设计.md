## 1. `[sources]`：通配符登记

### 1.1 写法

```toml
[sources]
files = ["guides/forms/*.md", "docs/**/*.md"]

[sources.shot]          # 非 Markdown 材料：名字要先在 [adapters] 里声明
files = ["videos/*.mp4"]
```

- 只写本地路径：相对仓库根目录，`/` 分隔，不分大小写。网址不能写在这里，仍用 `refcov add <网址> --id …`，由用户运行。
- `refcov add` 登记的源照常有效，和 `[sources]` 展开的源并存。
- 匹配用现有的 `store.path_matches`。它的 `*` 也能跨 `/`（示例配置开头的注释写明了），所以 `guides/forms/*.md` 也会匹配 `guides/forms/a/b.md`。这是决定 3：保持，并写明。
- 没有 `[[scope]]` 时，所有写入都要求读完全部参考源（需求 8.2）。只写 `[sources]` 一行就能用。

### 1.2 生成的编号

形式：`f-<路径片段>-<小写路径的 sha256 前 6 位>`，例如 `f-guides-forms-date-picker-md-3a9c1d`。

- 路径片段：路径转小写，只保留 a–z、0–9，其他字符换成 `-`，合并连续的 `-`，去掉首尾的 `-`，最多 40 个字符。片段为空（例如文件名全是中文）时用 `x`。
- 同一路径每次得到同一个编号。不同路径得到不同编号（哈希后缀保证）。登记时仍检查一次，撞了就报错，不静默改名。
- 编号只含 a–z、0–9 和 `-`，没有空白和方括号。
- 路径改名就是新编号；旧编号按 1.5 处理。

### 1.3 `refcov sync`

用户运行。在仓库根目录运行，只有用户能运行（`USER_ONLY`）。

1. 列出 `[sources]` 匹配到的文件，算出编号。
2. 和清单比较：
   - 新增：匹配到，清单里没有 → 登记。
   - 改动：清单里有，内容的 SHA-256 变了 → 重新登记（内容变了的单元，旧读取不再有效，需求 1.4）。
   - 文件已不在：清单里有、配置仍匹配、但文件不在了 → 不动，缓存里的副本仍可读，仍必看。
   - 已移出：清单里有，但 `refcov.toml` 改过、不再匹配 → 不再必看（1.5）。
3. 打印四组清单。没有变化时只打印一行。
4. 记一条 `sync` 日志：`refcov.toml` 的修改时间（纳秒）和本次的编号列表（见 1.5）。

报告（`report`、`check`）只读，不同步。它们列出"有 N 个匹配文件还没登记"和"有 N 个文件已变但还没同步"。钩子和 MCP 只读已登记的内容。

### 1.4 为什么 B，不是 A

需求 14 保护的是状态目录和配置文件（14.1–14.2），并用文本匹配拦 shell 里对它们和钩子脚本的操作（14.4；拦 `.kiro/hooks` 目录是用户 2026-11-12 另加的，需求原文没有）。材料文件不在保护范围内，AI 能在匹配路径下新建、修改、删除文件。所以"AI 加不了材料"只对配置成立，对匹配路径下的文件不成立。

A 方案（钩子和 MCP 自动同步）会留下两个洞：

1. 造材料再引用：AI 在匹配路径下新建文件，它被自动登记，AI 读它（覆盖 100%），再在需求里引用它，出处检查通过。
2. 删正文减必看：AI 改已登记的材料，内容变了就自动重新登记，单元数可能变少，旧单元不再必看。

B 两个洞都堵住：新文件和改动的文件要用户运行 `refcov sync` 才登记。代价是加材料或改材料后要多运行一次。

### 1.5 移出清单、文件消失、改名

由 1.3 的 `sync` 日志记录决定。记 `R` 为最近一条 `sync` 记录，`cur` 为当前 `refcov.toml` 的修改时间：

- `cur` 等于 `R` 记下的时间（配置没改过）：必看的自动源是 `R` 里的编号，不管文件在不在。文件被删或改名，仍必看。
- `cur` 不等于 `R` 记下的时间（配置改过）：必看的自动源是 `R` 里的编号中、现在仍匹配的那些。不再匹配的就是移出清单，不再必看。

被需求引用的单元始终必看（需求 6.5，不论在哪个参考源），所以引用不会因为移出而变松。手动登记（`refcov add`）的源不受这一节影响。

`sync` 记录的编号列表怎么算：配置没改过时，保留 `R` 的编号（缺的文件也留着），再加上本次匹配到的编号；配置改过时，只保留本次仍匹配的编号。

### 1.6 非 Markdown 材料

- 写成 `[sources.<名字>]`，名字必须在 `[adapters]` 里声明（骨架需求 2.1 已有的机制）。例：`[adapters] shot = "apps/shot-coverage/adapter.py"`，然后 `[sources.shot] files = ["videos/*.mp4"]`。
- 适配器是代码，在 RefCov 进程里运行。只声明用户信任的文件（示例配置的注释已写明）。

### 1.7 配置错误

报告里列为配置问题（沿用 `coverage.py` 第 114 行的 `config_problems`）：

- 写了网址：不登记。
- 某条通配符一个文件都没匹配：写明是哪一条。
- `[adapters]` 里没有这个名字。
- 同一个文件既用 `refcov add` 登记过，又被 `[sources]` 展开：两个源，同一内容，单元重复。

### 1.8 耗时

测得（本机，Windows）：

- 解释器启动，`python -c pass`，5 次 64–108 毫秒。钩子每次都要付这个成本，与本设计无关。
- `docs/` 下 19 个文件、624,660 字节：stat 合计 1.2 毫秒；sha256 合计 0.5 毫秒。

推测（未测）：210 份前端指南（约 2 MB）时，stat 约 14 毫秒，sha256 约 2 毫秒。

影响：B 方案下钩子不做文件检查，不新增文件操作。`sync` 才读材料文件。

没测：首次登记 210 份（拆分和写缓存）的耗时。实现后要用这批材料实测，再写数字。

### 1.9 加锁

- 写清单、写缓存、写日志都在 `log.lock` 里，沿用现有的锁（`refcov/store.py`：`O_EXCL`，每 50 毫秒重试，最多等 2 秒，超过 10 秒的锁当残留删掉）。不新增锁。
- 只读的命令（`report`、`check`，以及钩子）不拿锁。

### 1.10 对照需求 14

- 14.1–14.2：`refcov.toml` 只能由用户改，AI 不能改清单。成立。
- 14.3：会写读取记录的入口只有 MCP 工具和钩子。`sync` 只写登记和同步记录，不写读取记录，而且只能由用户运行。成立。
- 14.4：shell 命令文本匹配。`refcov sync` 加进 `USER_ONLY`，AI 在 shell 里运行会被拦。成立。
- 需求 14 没有覆盖：匹配路径下的材料文件（1.4）。B 方案靠"只用已登记内容"处理。

## 6. 和已有决定的关系

- `docs/decisions/2026-11-10-design-review.md` 第 1 条（MCP 单元 `dec-design-review/1-shell-里拦-init，放行-add`）写的是：shell 里 `refcov add` 放行，理由是"只会让覆盖率变低"。后来的骨架设计（`.kiro/specs/refcov-skeleton/design.md` 第 293 行）改成拦，理由是同一个编号登记一个小文件，覆盖率会变成 100%。代码按后来的设计实现。本设计也按"拦"。
- 本设计新增的 `refcov sync` 是用户命令，同样拦截。`setup.py` 不是 `refcov` 的命令，AI 运行只会补装，不影响覆盖率判断。
